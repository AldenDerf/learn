# Lab 2.1: Static IP & Host–VM Connectivity

**Draft for instructor review · ITM 402 · Module 2**

**Task:** Assign static IP coordinates on the server node and verify Host–VM connectivity. Work through [2.1 Local Networking & Subnetting](/sys-admin/module-2/local-networking) first.

## Goal and preparation

By the end, explain what you configured, why you configured it, how you verified it, and what you checked when a test failed. Two successful pings alone are not a complete submission.

Use an installed Ubuntu Server VM, a Windows host, VirtualBox, and the VM's local console. Have an instructor-approved snapshot before network changes; a snapshot is a saved VM state you can restore. Use the console rather than a remote session that could disconnect. Record your Ubuntu and VirtualBox versions.

```text
Windows host: 192.168.56.1/24
             |
    VirtualBox Host-Only network
             |
Ubuntu VM:   192.168.56.10/24

Optional separate path: Ubuntu NAT adapter -> Internet
```

The examples assume this subnet is unused by your LAN/VPN. If it overlaps, ask the instructor to assign another subnet and change all addresses consistently. A silent ping does not prove an address is unused; inspect the lab address plan and existing assignments.

## 1. Inspect the current configuration

In Ubuntu, run:

```bash
ip addr
ip route
hostname -I
```

`ip addr` lists interfaces and their addresses; record `inet` IPv4 values and prefixes. `ip route` shows where packets go; record the default route, if any. `hostname -I` (capital `I`) gives a quick address summary. Keep this output as your **before** evidence. Do not confuse `127.0.0.1` on `lo` with the VM's lab address.

In Windows PowerShell, run:

```powershell
ipconfig
```

`ipconfig` displays Windows adapter addresses. Identify the VirtualBox Host-Only adapter separately from Wi-Fi/Ethernet. Record its IPv4 address and subnet mask; it may not exist until the next step.

## 2. Inspect VirtualBox Host-Only networking

Shut down the VM normally before changing its virtual adapters.

1. Open VirtualBox's **Tools → Network** (called **Host Network Manager** in some versions). Select or create a Host-Only network for this lab.
2. Inspect the host adapter's IPv4 settings. For this example use `192.168.56.1` with mask `255.255.255.0`. Do not change the Windows Wi-Fi adapter.
3. Disable VirtualBox's DHCP server for this dedicated lab network. We will assign the server address ourselves, and later study a separate DHCP server.
4. Open the VM's **Settings → Network**. Keep Adapter 1 as NAT if you need downloads. Enable Adapter 2, choose **Host-Only Adapter**, and select the network from step 1. Ensure **Cable Connected** is checked.
5. Record Adapter 2's MAC address under its advanced settings. Boot Ubuntu and run `ip addr` again. Match that MAC to the `link/ether` value; VirtualBox may display the same hexadecimal digits without colons. This identifies the interface to configure.
6. Run `ipconfig` on Windows again to verify the actual host address.

The remaining example uses `enp0s8`. Substitute the name you identified. If you cannot match the adapter, stop and resolve that before editing.

## 3. Inspect and back up Netplan

```bash
ls /etc/netplan
sudo netplan get
```

`ls` lists file names in Netplan's configuration directory. `sudo netplan get` shows the merged configuration; `sudo` grants administrator privileges for reading protected configuration. Identify the file defining the Host-Only interface. If there are several definitions or a file says it is generated by cloud-init, have the instructor resolve ownership before continuing; generated settings can be replaced on reboot.

The following examples assume the discovered file is `/etc/netplan/50-cloud-init.yaml`. Use your actual file name throughout, even if it differs.

```bash
sudo cp /etc/netplan/50-cloud-init.yaml /etc/netplan/50-cloud-init.yaml.lab21-backup
sudo nano /etc/netplan/50-cloud-init.yaml
```

`cp` copies the existing file to a backup. The backup does not end in `.yaml`, so Netplan will not read it as configuration. Use a fresh backup name if one already exists so you preserve the original. `nano` opens a terminal text editor. These commands need `sudo` because system configuration is protected. If the Host-Only interface has no definition, the instructor can help create a dedicated `.yaml` file containing only its stanza; record that new file for recovery.

## 4. Configure the static address

Edit the Host-Only interface under the existing `network` → `ethernets` mapping. Preserve the NAT interface and other existing settings. Do not paste a second `network:` block into the file.

For a VM whose NAT interface is `enp0s3` and Host-Only interface is `enp0s8`, a complete simple configuration looks like this:

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp0s3:
      dhcp4: true
    enp0s8:
      dhcp4: false
      addresses:
        - 192.168.56.10/24
```

- `network` groups all settings; `version: 2` selects Netplan's format.
- `renderer: networkd` uses Ubuntu Server's network service. Confirm this matches the installed image.
- `ethernets` groups Ethernet adapters. Each interface name is a key.
- `dhcp4: true` preserves automatic IPv4 settings for NAT.
- `dhcp4: false` disables automatic IPv4 allocation on the lab interface.
- `addresses` is a list; its indented dash assigns `.10` with prefix `/24`.

Indent using spaces only. Settings for both interfaces must line up at the same level. No Host-Only default gateway or DNS setting is needed to ping by IP on this local subnet. Do not copy `enp0s3` if your NAT interface has another name or there is no NAT adapter.

In nano, press **Ctrl+O**, then **Enter** to save; **Ctrl+X** exits. Before applying, explain to your partner which lines assign the address and which lines preserve downloads.

## 5. Validate and apply

```bash
sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan generate
sudo netplan try
sudo netplan apply
```

Use the actual file name. `chmod 600` restricts this configuration to its owner (normally root); `6` gives owner read/write, and both zeros deny group/other access. `netplan generate` checks and translates the YAML without applying it. Fix any errors it reports before proceeding.

`netplan try` temporarily applies the settings and asks for confirmation. At the local console, verify the address and connectivity before confirming within the displayed timeout. If necessary, use a second VM console. A timeout is intended to revert settings, but always inspect the actual state afterward; do not assume rollback succeeded. `netplan apply` applies the saved configuration; run it once the validated settings are correct. No output usually means no error was reported, not proof of connectivity.

## 6. Verify the assigned address and route

```bash
ip addr show enp0s8
ip route
hostname -I
```

`show enp0s8` narrows the address view to your lab interface. Look for `inet 192.168.56.10/24`. In the route list, expect a directly connected route for `192.168.56.0/24` on that interface. The address summary should include `.10`; it can also include the NAT address and IPv6 addresses.

Record the **after** output. If two IPv4 addresses appear unexpectedly on the lab interface, inspect merged Netplan settings instead of declaring success.

## 7. Test Windows host to Ubuntu VM

In Windows PowerShell:

```powershell
ping -n 4 192.168.56.10
```

Windows `ping` sends Echo requests; `-n 4` requests four tests. The destination is the VM's static address. Record replies, packet loss, and the exact destination. Ubuntu uses `-c`, not Windows's `-n`, for the count.

## 8. Test Ubuntu VM to Windows host

In Ubuntu:

```bash
ping -c 4 192.168.56.1
```

`-c 4` sends four requests to the Windows Host-Only address. Successful replies in both directions support local reachability. They do not test Internet access, DNS, or application availability.

Windows may block inbound Echo requests. If only VM → host fails, inspect Windows Defender Firewall with the instructor. If permitted, create a narrowly scoped inbound ICMPv4 Echo rule for the Host-Only adapter/local address and the VM's source address, with the appropriate network profile. Keep the firewall enabled; do not enable broad access on the physical network. Record and remove any temporary lab rule afterward. Also inspect Ubuntu firewall policy if host → VM fails.

## 9. Troubleshoot with evidence

- Is the VM running?
- Is the correct adapter enabled and its virtual cable connected?
- Is Host-Only selected, and is it the same network as the Windows adapter?
- Is the interface name correct, confirmed by MAC address?
- Are both devices in the same subnet, with the same intended prefix and different IPs?
- Is Netplan YAML indentation correct, using spaces and no duplicate keys?
- Did `sudo netplan generate` succeed?
- Was `sudo netplan apply` executed successfully?
- What does `ip addr` show now, not just before the edit?
- Does `ip route` show the connected subnet on the expected interface?
- Can both systems ping each other? Which direction fails?
- Do scoped firewall rules permit Echo requests and replies?

| Symptom | First useful check |
| --- | --- |
| Interface missing | VirtualBox adapter enabled; match the MAC again |
| YAML parse error | Reported line, nearby indentation, tabs, and duplicate keys |
| Old or unexpected address | Correct file/interface; merged Netplan definitions; apply result |
| Destination host unreachable | Link, subnet, target address, duplicate IP, and local route |
| Request timed out | Destination running, return path, and firewall; timeout alone does not identify the cause |
| Local ping works but Internet does not | NAT adapter and default route; Host-Only does not supply Internet |

Change one thing at a time and repeat the same test. Record the symptom, evidence, hypothesis, correction, and result.

## Recovery and persistence check

If editing the existing file caused a failure, use the VM console to restore your backup:

```bash
sudo cp /etc/netplan/50-cloud-init.yaml.lab21-backup /etc/netplan/50-cloud-init.yaml
sudo netplan generate
sudo netplan apply
```

`cp` restores the saved contents; generate validates them, and apply activates them. Substitute your recorded filenames. If you created a separate new YAML file, move that new file to a backup name ending in `.disabled` with the instructor before applying the original configuration. Verify actual addresses afterward. Use the VM snapshot if the original state cannot be recovered reliably.

When the intended configuration works, reboot the VM through its normal shutdown/restart controls. Repeat address and two-way ping checks to confirm persistence. Keep the configuration for the next lesson unless the instructor asks you to restore it.
