# Lab 2.1: Static IP & Host–VM Connectivity

**Draft for instructor review · ITM 402 · Module 2**

## Goal

**Make your Windows computer and your Ubuntu Server VM communicate with each other.**

In this lab, you will assign a permanent (**static**) IP address to your Ubuntu Server VM. Then, you will test that both computers can talk to each other across a private virtual network.

Make sure you have read [2.1 Local Networking & Subnetting](/sys-admin/module-2/local-networking) before starting.

```text
+-----------------------------------+             +-----------------------------------+
|           Windows Host            |             |         Ubuntu Server VM          |
|      (Your Physical Computer)     |             |      (Virtual Machine Console)    |
|                                   |             |                                   |
|   VirtualBox Host-Only Adapter    |  Host-Only  |       Host-Only Interface         |
|         192.168.56.1/24           |<===========>|        192.168.56.10/24           |
+-----------------------------------+   Network   +-----------------------------------+
                                                                    |
                                                                    | NAT (Adapter 1)
                                                                    v
                                                            Internet Downloads
```

### Two connections at a glance

| Connection | VirtualBox Name | What it is used for in this lab |
| --- | --- | --- |
| **Host-Only** | Adapter 2 | Private line between Windows and Ubuntu for lab communication |
| **NAT** | Adapter 1 | Allows Ubuntu to download packages from the Internet |

By the end of this lab, you will understand:
- **What** you configured on both machines.
- **Why** the server needs a static IP address.
- **How** to verify the connection using `ip addr` and `ping`.
- **Where** to look when communication fails.

---

## Before you start

1. **Work inside the VM window (the local console):** Do not configure network settings over SSH yet. If you make a mistake in your network file, an SSH session will disconnect and lock you out. The VM window will always stay connected.
2. **Take a VM snapshot:** In VirtualBox, take a snapshot of your VM before editing any files (e.g., name it `Before-Lab-2.1`). If anything goes wrong, you can restore this snapshot in seconds.
3. **Keep both firewalls enabled:** Do not turn off Windows Firewall or Ubuntu's firewall completely.
4. **Remember your actual names:** Interface names like `enp0s8` and filenames like `00-installer-config.yaml` are examples. Always use the actual names you find on your machine.

## Step 1 — Check the current network configuration

**What we are doing:** Recording the network addresses on both computers before changing anything.

**Why:** We need to know our starting point so we can tell if our changes worked.

### Part A: On Ubuntu Server (VM Console)

Run this command in your Ubuntu terminal:

```bash
ip addr
```

- **What it does:** Shows all network interfaces and their assigned IP addresses.
- **What to look for:** Find lines starting with `inet`. You might see `127.0.0.1` under `lo` (this is loopback, the server talking to itself). You might see a `10.0.2.x` address under `enp0s3` (this is the NAT adapter).
- **Write down:** The interface names you see (for example: `lo`, `enp0s3`).

### Part B: On Windows (PowerShell)

Open **PowerShell** on your Windows host computer and run:

```powershell
ipconfig
```

- **What it does:** Displays the IP addresses of all network adapters on Windows.
- **What to look for:** Look for a section named `Ethernet adapter VirtualBox Host-Only Network`. If it is already there, note its IPv4 address (usually `192.168.56.1`).
- **If you don't see it:** Don't worry. Step 2 will create or enable it.

## Step 2 — Configure or verify VirtualBox Host-Only networking

**What we are doing:** Setting up a dedicated virtual network switch inside VirtualBox so Windows and Ubuntu can connect.

**Why:** Devices cannot communicate if they are plugged into different networks.

### Action steps

1. **Shut down your Ubuntu VM** cleanly:
   ```bash
   sudo poweroff
   ```
2. **Open VirtualBox Manager** on Windows.
3. **Open the Network Manager:**
   - In VirtualBox 7, click the **Tools** menu icon (next to the machine list) and select **Network**. (In older versions, go to **File → Host Network Manager**).
4. **Check the Host-Only network:**
   - Look for `VirtualBox Host-Only Ethernet Adapter`. If none exists, click **Create**.
   - Under the **Adapter** tab:
     - **IPv4 Address:** `192.168.56.1`
     - **IPv4 Network Mask:** `255.255.255.0` (this means `/24`).
   - Under the **DHCP Server** tab:
     - Make sure **Enable Server** is **UNCHECKED (Disabled)** for this lab network. We will set our IP addresses manually.
5. **Attach the adapter to your Ubuntu VM:**
   - Click on your Ubuntu VM, then click **Settings → Network**.
   - **Adapter 1:** Keep attached to **NAT** with **Cable Connected** checked. (This gives Ubuntu Internet access to download packages).
   - **Adapter 2:**
     - Check **Enable Network Adapter**.
     - Attached to: select **Host-Only Adapter**.
     - Name: select `VirtualBox Host-Only Ethernet Adapter` (the one with `192.168.56.1`).
     - Click **Advanced** and make sure **Cable Connected** is checked.
     - **Note down the MAC Address** shown here (e.g., `080027123456`). You will need it in Step 3.
6. Click **OK** to save settings, then **Start your Ubuntu VM**.

**What should happen:** Windows has a virtual adapter at `192.168.56.1`, and Ubuntu has a second virtual network card attached to the exact same virtual network.

**If it fails:** Make sure you chose **Host-Only Adapter**, NOT "Bridged Adapter" or "Internal Network".

## Step 3 — Find the Ubuntu Host-Only interface

**What we are doing:** Finding out what Ubuntu calls the second adapter you just enabled.

**Why:** If we configure the wrong interface, we might break Internet access or configure nothing at all.

### Action steps

1. In VirtualBox, remember the **Adapter 2 MAC Address** you saw in Step 2 (for example, `080027123456`).
2. Log in to Ubuntu and run:
   ```bash
   ip addr
   ```
3. Look at each interface for the line starting with `link/ether`:
   ```text
   3: enp0s8: <BROADCAST,MULTICAST> ...
       link/ether 08:00:27:12:34:56 brd ff:ff:ff:ff:ff:ff
   ```
4. Match the numbers! Notice how VirtualBox wrote `080027123456` and Linux writes `08:00:27:12:34:56`. They are the exact same physical ID (MAC address).
5. The interface name right above the matching MAC address is your Host-Only interface (in this example: `enp0s8`).

> [!NOTE]
> **Do not guess!** Your interface might be named `enp0s8`, `enp0s9`, or `eth1`. Always match the MAC address to be 100% sure.

## Step 4 — Configure the static IP using Netplan

**What we are doing:** Writing our server's static IP address (`192.168.56.10/24`) into Ubuntu's network configuration file.

**Why:** A static IP written in Netplan is permanent. It stays the same every time the server boots up.

### Golden rules of Netplan YAML

Netplan configuration files use a format called **YAML**. YAML has strict rules:
1. **Never press the Tab key.** Always use the Space bar for indentation.
2. **Indentation shows hierarchy:** Use exactly 2 spaces per indentation level.
3. **Preserve existing settings:** Do not delete your NAT interface (`enp0s3`), or your server will lose Internet access.

### 4.1 Find your Netplan file

Run:
```bash
ls /etc/netplan
```

Look for a file ending in `.yaml` (for example, `00-installer-config.yaml` or `50-cloud-init.yaml`). Write down its exact name.

### 4.2 Make a safety backup

Before editing any system configuration file, always create a backup copy:

```bash
sudo cp /etc/netplan/00-installer-config.yaml /etc/netplan/00-installer-config.yaml.lab21-backup
```
*(Replace `00-installer-config.yaml` with your actual filename).*

If you ever make a mistake, this backup file allows you to restore working settings immediately.

### 4.3 Open the file in the nano editor

```bash
sudo nano /etc/netplan/00-installer-config.yaml
```

### 4.4 Understand the change (Before vs After)

Here is what typical Netplan files look like before and after your edit:

#### BEFORE (Only NAT was configured):
```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp0s3:
      dhcp4: true
```

#### AFTER (Both NAT and Host-Only are configured):
```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp0s3:
      dhcp4: true
    enp0s8:
      dhcp4: false
      addresses:
        - 192.168.56.10/24
```

### What each line means

| Setting | Value in example | Simple explanation |
| --- | --- | --- |
| `renderer:` | `networkd` | Tells Ubuntu to use `systemd-networkd` to manage the network. |
| `enp0s3:` | `dhcp4: true` | Adapter 1 (NAT): get an IP automatically so we can reach the Internet. |
| `enp0s8:` | (Your interface from Step 3) | Adapter 2 (Host-Only): our private lab connection. |
| `dhcp4:` | `false` | Turn off automatic IP for this interface. We want a fixed address. |
| `addresses:` | `- 192.168.56.10/24` | Assign static IP `192.168.56.10` with subnet mask `/24` (`255.255.255.0`). |

> [!IMPORTANT]
> **Notice there is NO gateway line for `enp0s8`!** Windows (`192.168.56.1`) is just a neighbor on the same network, not a router. Internet traffic still flows through NAT (`enp0s3`).

### 4.5 Save and exit nano

1. Press **Ctrl + O** (WriteOut).
2. Press **Enter** to confirm the filename.
3. Press **Ctrl + X** to exit nano.

## Step 5 — Validate and apply the configuration

**What we are doing:** Checking the file for formatting mistakes, then applying the new network settings.

**Why:** Testing the file first prevents network crashes caused by simple typing mistakes.

### 5.1 Set secure file permissions

Netplan requires configuration files to be readable only by root:

```bash
sudo chmod 600 /etc/netplan/00-installer-config.yaml
```

### 5.2 Test for syntax errors

Run:

```bash
sudo netplan generate
```

- **What it does:** Reads the YAML file and checks if the formatting and indentation are correct.
- **What to look for:**
  - **If it outputs NOTHING:** That is great news! Silence means there were no syntax errors.
  - **If it shows an error:** Read the error carefully. It will tell you the exact line number where you have a spacing or indentation problem. Reopen nano, fix the spacing, and run `netplan generate` again.

### 5.3 Apply the configuration

Once `netplan generate` succeeds with no errors, apply the settings:

```bash
sudo netplan apply
```

**What should happen:** The command finishes silently in 1–2 seconds. Ubuntu has now applied your static IP.

**If it fails:** Do not panic. Check [Recovery](#recovery-restore-the-backup) to restore your backup if needed.

## Step 6 — Check the Ubuntu IP address

**What we are doing:** Verifying that Ubuntu is now actively using `192.168.56.10`.

**Why:** Never assume a command worked just because it did not show an error. Always verify the actual state.

Run:

```bash
ip addr
```

Find your Host-Only interface (`enp0s8`). You should now see:

```text
3: enp0s8: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
    inet 192.168.56.10/24 brd 192.168.56.255 scope global enp0s8
```

You can also run a quick summary check:

```bash
hostname -I
```

- **What to look for:** You should see `192.168.56.10` in the output list.
- **What it means:** Success! Ubuntu Server has claimed `192.168.56.10` on the Host-Only network.

## Step 7 — Ping Ubuntu from Windows

**What we are doing:** Sending test messages from Windows to Ubuntu to see if Windows can reach the server.

**Why:** This proves that inbound traffic from your host computer reaches the VM.

Open **PowerShell on Windows** and run:

```powershell
ping -n 4 192.168.56.10
```

*(Note: On Windows, `-n 4` sends 4 test packets).*

### Expected output (Success)

```text
Pinging 192.168.56.10 with 32 bytes of data:
Reply from 192.168.56.10: bytes=32 time<1ms TTL=64
Reply from 192.168.56.10: bytes=32 time<1ms TTL=64
Reply from 192.168.56.10: bytes=32 time<1ms TTL=64
Reply from 192.168.56.10: bytes=32 time<1ms TTL=64

Ping statistics for 192.168.56.10:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)
```

**What this proves:** Windows successfully sent 4 packets to Ubuntu, and Ubuntu successfully replied to all 4!

**If it fails:** If you see `Request timed out` or `Destination host unreachable`, go to [Step 9](#step-9--troubleshoot-if-communication-does-not-work).

## Step 8 — Ping Windows from Ubuntu

**What we are doing:** Sending test messages from Ubuntu to Windows to test the reverse direction.

**Why:** Network communication is a two-way street. Testing Windows → Ubuntu does not guarantee Ubuntu → Windows works.

In your **Ubuntu console**, run:

```bash
ping -c 4 192.168.56.1
```

*(Note: On Linux, `-c 4` sends 4 test packets).*

### Expected output (Success)

```text
PING 192.168.56.1 (192.168.56.1) 56(84) bytes of data.
64 bytes from 192.168.56.1: icmp_seq=1 ttl=128 time=0.421 ms
64 bytes from 192.168.56.1: icmp_seq=2 ttl=128 time=0.380 ms
64 bytes from 192.168.56.1: icmp_seq=3 ttl=128 time=0.410 ms
64 bytes from 192.168.56.1: icmp_seq=4 ttl=128 time=0.395 ms

--- 192.168.56.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3074ms
```

### What if this ping fails?

If Ubuntu says `100% packet loss` when pinging Windows, but Step 7 (Windows → Ubuntu) succeeded:
- **Don't panic:** Your IP configuration is almost certainly correct!
- **The culprit:** Windows Defender Firewall blocks incoming ICMP (ping) requests by default on private adapters. See [Check firewall rules with the instructor](#check-firewall-rules-with-the-instructor) below to understand why.

## Step 9 — Troubleshoot if communication does not work

**What we are doing:** Following a systematic checklist to diagnose the exact issue.

**Why:** Good system administrators do not guess; they gather evidence.

### Diagnostic checklist

Work through these questions one by one:

1. **Is the VM running?** If the VM is suspended or powered off, no packets can be delivered.
2. **Is VirtualBox Adapter 2 enabled with Cable Connected?** Go to VM Settings → Network → Adapter 2 → Advanced → ensure **Cable Connected** is checked.
3. **Does Windows have `192.168.56.1`?** Run `ipconfig` in Windows PowerShell. Check the `VirtualBox Host-Only Network` section.
4. **Does Ubuntu have `192.168.56.10`?** Run `ip addr` on Ubuntu. Does `192.168.56.10/24` appear under your Host-Only interface?
5. **Did you type the IP addresses correctly?** Both addresses must start with `192.168.56.` and end with different numbers (`.1` on Windows, `.10` on Ubuntu).
6. **Did you use spaces in Netplan?** Tabs cause Netplan to fail silently or throw errors. Re-check `/etc/netplan/00-installer-config.yaml`.
7. **Which direction failed?**
   - If **Windows → Ubuntu** fails: Recheck Ubuntu's IP (`ip addr`) and check if Adapter 2 is attached to Host-Only.
   - If **Ubuntu → Windows** fails: Recheck Windows Firewall settings.

## Focused troubleshooting

### Check the route

A **route** tells Ubuntu which doorway to use when sending data to a specific network:

```bash
ip route
```

**What to look for:**
- You should see a line for `192.168.56.0/24 dev enp0s8` (where `enp0s8` is your Host-Only interface).
- You should see `default via 10.0.2.2 dev enp0s3` (this is the NAT default gateway for Internet).
- **Important:** There should be NO default route pointing to `192.168.56.1`. Windows is not acting as your Internet router!

### Common symptoms and quick fixes

| Symptom | Most likely cause | What to check / do |
| --- | --- | --- |
| Interface missing from `ip addr` | Adapter 2 disabled in VirtualBox | Shut down VM, enable Adapter 2 in VirtualBox settings, start VM |
| `Invalid YAML at line X` | Pressed Tab key or wrong indentation | Open file in nano, remove tabs, use 2 spaces per level |
| Old IP address still shows | `netplan apply` was not run | Run `sudo netplan generate && sudo netplan apply` |
| `Destination host unreachable` | Host-Only network not connected or wrong subnet | Verify VirtualBox Network Manager settings and adapter attachment |
| `Request timed out` (Ubuntu → Windows) | Windows Firewall blocking incoming ping | See firewall section below; do not disable the firewall completely |
| Internet package downloads fail | NAT adapter altered or default route removed | Ensure `enp0s3` still has `dhcp4: true` in your Netplan file |

### Check firewall rules with the instructor

By default, Windows Defender Firewall drops incoming ICMP Echo (ping) requests. If Windows can ping Ubuntu, but Ubuntu cannot ping Windows:

1. On Windows, open **PowerShell as Administrator**.
2. To allow incoming pings **only on the private VirtualBox adapter**, an instructor may recommend running:
   ```powershell
   New-NetFirewallRule -DisplayName "Allow ICMPv4 for VirtualBox Lab" -Direction Inbound -Protocol ICMPv4 -IcmpType 8 -Action Allow -InterfaceAlias "VirtualBox Host-Only Network"
   ```
3. Test `ping -c 4 192.168.56.1` from Ubuntu again.
4. **Security rule:** Never turn off Windows Firewall completely. Restricting the rule to the specific VirtualBox interface keeps your computer safe on Wi-Fi.

## Recovery: restore the backup

If you made an error in your Netplan configuration and cannot get it to work, use your backup file to restore the original working state:

```bash
sudo cp /etc/netplan/00-installer-config.yaml.lab21-backup /etc/netplan/00-installer-config.yaml
sudo netplan generate
sudo netplan apply
```

Then run `ip addr` to confirm your system has returned to its initial state. If needed, you can also revert to the VirtualBox snapshot you took before the lab.

## Optional: Netplan try

Before permanently saving changes, Netplan has a built-in safety feature called `netplan try`:

```bash
sudo netplan try
```

- **What it does:** Temporarily applies the configuration and gives you a countdown timer (usually 120 seconds).
- **How it works:** If you press **Enter**, the changes become permanent. If you do nothing (or if you get disconnected), Netplan automatically rolls back to the previous configuration when the timer expires.

## Instructor notes

- **Subnet conflicts:** Verify that `192.168.56.0/24` does not collide with the student's physical home or campus LAN/Wi-Fi subnet. If a collision occurs, assign a different subnet (e.g., `192.168.99.0/24`) and have students adjust addresses accordingly.
- **Cloud-init files:** On cloud or server installations, `50-cloud-init.yaml` may exist. If present, explain that cloud-init generates network configuration automatically on boot unless disabled.
- **Multiple YAML files:** Netplan merges all `.yaml` files in lexicographical order. Ensure students only have one active configuration file defining their interfaces.
- **Network renderers:** This lab standardizes on `renderer: networkd` for Ubuntu Server. Desktop Ubuntu installs often use `NetworkManager`.
