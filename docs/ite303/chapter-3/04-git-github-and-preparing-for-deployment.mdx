## Part 1 — Why Developers Need Git and GitHub

### Saving versions of a school project

Imagine writing a major school paper. Have you ever saved files like this?

```text
research-paper.docx
research-paper-v2.docx
research-paper-final.docx
research-paper-FINAL-fixed-real.docx
```

When a software project has many files (`server.ts`, `db.ts`, `studentRoutes.ts`, `studentController.ts`, `package.json`), copying the whole folder every time you make a change becomes messy and confusing. It is hard to remember what changed between folders or which copy actually works.

**Version control** solves this problem. It tracks changes inside your existing project folder over time. Instead of duplicating folders, you save a clear checkpoint whenever a feature works.

### What is Git?

**Git** is a free version control tool installed on your computer. It watches your project folder, records what lines changed in which files, and lets you save named checkpoints called **commits**. Git works on your computer even when you have **no internet connection**.

### What is GitHub?

**GitHub** is a website that stores Git projects online. When you connect your local Git project to GitHub, you can upload your saved checkpoints to the cloud, back up your code, share your work with your instructor, and connect your project to deployment platforms.

### Git vs. GitHub at a glance

| Feature | Git | GitHub |
| --- | --- | --- |
| **What it is** | Version control software installed on your computer | A website and cloud service that hosts Git repositories online |
| **Where it runs** | Locally on your computer | On the internet (in your web browser) |
| **Needs internet?** | No — you can inspect changes and create commits offline | Yes — uploading (`push`) or downloading (`pull`) requires internet |
| **Main job** | Track file changes and save version history | Back up repositories, support collaboration, and connect to deployment services |

### Why developers save changes through commits

Instead of saving one giant update at the end of the semester, developers save small, logical checkpoints (**commits**) as they build:

- **Clear history:** Each commit has a short message explaining *what* changed and *why* (for example, `Add README endpoint summary`).
- **Safety net:** If a future edit breaks your API, you can compare your broken file against the last working commit to see exactly what changed.
- **Deployment readiness:** Cloud platforms deploy specific commits from your repository so they know exactly which version of your code to run.

### Key terms explained simply

Read through this table before setting up your tools. You will use these words throughout the rest of the course:

| Term | Simple meaning |
| --- | --- |
| **Repository (repo)** | A project folder that Git is tracking, including all its files and saved version history. |
| **Local repository** | The copy of the repository stored on your own computer. |
| **Remote repository** | The copy of the repository stored online on GitHub. |
| **Commit** | A saved snapshot (checkpoint) of your tracked files at a specific moment, labeled with a short message. |
| **Push** | Uploading your new local commits from your computer to your remote repository on GitHub. |
| **Pull** | Downloading new commits from GitHub to update the local repository on your computer. |
| **Branch** | A separate workspace timeline inside a repository where you can try changes without affecting the main working version. |
| **Main branch (`main`)** | The default, primary branch of a repository where the official working version of your project lives. |

We will keep all of our work on the **`main` branch** in this lesson. You do not need complex branching workflows yet.

## Part 2 — Installing Required Tools

You need three things for this workflow: **Git**, a **GitHub account**, and **GitHub Desktop**. Follow these Windows steps in order. If a tool is already installed on your machine, verify it using the checkpoint steps.

### 1. Install Git for Windows

Git does the version tracking behind the scenes on your computer.

1. Open the official Git download page for Windows: [https://git-scm.com/install/windows](https://git-scm.com/install/windows) (or visit [https://git-scm.com/downloads](https://git-scm.com/downloads) and choose **Windows**).
2. Download the **64-bit Git for Windows Setup** installer.
3. Run the downloaded `.exe` installer.
4. Click **Next** through the setup screens to accept the standard default options.
   - If the installer asks for the default branch name, choose **`main`** (or leave the default and let GitHub Desktop set `main` later).
5. Click **Install**, then **Finish**.

### 2. Verify your Git installation

1. Open **PowerShell** or **Command Prompt** (or a new terminal inside VS Code).
2. Run this command to ask Git for its installed version:

```powershell
# Check that Git is installed and reachable in the terminal
git --version
```

**Expected result:** You should see output similar to `git version 2.47.1.windows.1` (your exact version number may be newer).

**If it fails:** If you see `'git' is not recognized`, close your terminal window completely (and close VS Code if it was open during installation), open a fresh terminal window, and run `git --version` again so Windows reloads its program path.

### 3. Create or sign into your GitHub account

1. Open [https://github.com](https://github.com) in your web browser.
2. If you already have an account, click **Sign in**.
3. If you do not have an account yet, click **Sign up** and follow the steps using an email address you can access.
4. **Verify your email address** if GitHub sends you a confirmation email. Unverified accounts cannot publish repositories.

**Tip:** Choose a clean, professional username (for example, based on your name). You will use this account for your projects and deployment chapters.

### 4. Install GitHub Desktop

**GitHub Desktop** gives you a clear visual window to see changed files, create commits, and publish to GitHub without memorizing terminal commands.

1. Open the official GitHub Desktop download page: [https://desktop.github.com/download/](https://desktop.github.com/download/).
2. Click **Download for Windows (64-bit)**.
3. Run the downloaded installer. GitHub Desktop installs automatically and opens when ready.

### 5. Sign into GitHub Desktop

1. In GitHub Desktop, click **Sign in to GitHub.com** (or go to **File → Options → Accounts** and click **Sign in** next to GitHub.com).
2. Your web browser will open and ask you to authorize GitHub Desktop. Click **Authorize desktop** and allow the browser to open GitHub Desktop again.
3. In the **Configure Git** screen (or under **File → Options → Git**), confirm that your **Name** and **Email** are filled in. Git attaches this name and email as the author label on every commit you create.
4. Click **Finish** or **Save**.

### 6. Confirm your existing Student API folder is on your computer

Before opening your project in GitHub Desktop, locate your **Student Information API** folder from Lesson 3.3 on your computer.

1. Open your project folder in **VS Code**.
2. Check the Explorer sidebar to confirm you are inside your **Student API project** (the folder that contains `package.json`, `.env`, and `src/server.ts`), **not** an empty folder and **not** a parent folder like `Desktop` or `Documents`.

**Checkpoint:** `git --version` prints a version number, you are signed into GitHub in your browser, GitHub Desktop shows your GitHub account under **File → Options → Accounts**, and your Student API folder is open in VS Code.

### Step 5 — Check `package.json`

Open `package.json` and confirm that it lists:

- Your `dev` script (for example, `"dev": "tsx watch src/server.ts"` or `"tsx src/server.ts"`).
- Your dependencies (`express`, `pg`, `dotenv`) and devDependencies (`typescript`, `tsx`, `@types/express`, `@types/pg`, etc.).

Because `package.json` records every package your project needs, you do **not** need to upload the massive `node_modules` folder to GitHub. Anyone (including a cloud deployment server) can recreate `node_modules` by running `pnpm install`.

### Step 6 — Ensure `.gitignore` exists

A **`.gitignore`** file is a plain text file in the root of your project. Each line tells Git which files or folders it must **ignore** and **never upload** to GitHub.

Look in the root of your Student API project (beside `package.json`). If `.gitignore` does not exist yet, create a new file named exactly **`.gitignore`** (notice the leading dot `.` and no `.txt` extension at the end).

### Step 7 & Step 8 — Ensure `.env` and `node_modules` are excluded

Open `.gitignore` and make sure it includes at least these rules:

```gitignore
# Dependency directory (recreated with pnpm install)
node_modules/

# Private environment variables and database credentials (NEVER commit!)
.env
.env.*
!.env.example

# Build output and logs
dist/
*.log

# Operating system files
.DS_Store
Thumbs.db
```

**Why each section matters:**
- `node_modules/` contains thousands of downloaded library files. Uploading it wastes data, slows down Git, and is unnecessary because `package.json` already lists your dependencies.
- `.env` and `.env.*` contain your real `DATABASE_URL` and Supabase database password. If uploaded to GitHub, anyone with access to the repository could read, modify, or delete your database.
- `!.env.example` tells Git: *"Even though `.env.*` is ignored, **do** allow the safe `.env.example` template file."*

<Callout type="warning">

**Critical security rule: `.gitignore` only prevents UNTRACKED files from being added.**

Adding `.env` to `.gitignore` does **not** erase secrets that were *already committed* to Git history in the past.

**What to do if you already committed `.env` or a real password:**
1. **STOP** immediately — do **not** publish or push the repository to GitHub.
2. **Inform your instructor** before taking further steps.
3. **Rotate (change) your exposed database password** in your Supabase project settings so the old leaked password can no longer be used.
4. Wait for instructor guidance to create a clean repository state. Do not try random terminal commands from the internet to rewrite Git history on your own.

</Callout>

### Step 9 — Create or check `.env.example` with placeholder values only

Since `.env` is ignored by Git, how will you (or your instructor) remember which environment variables your project needs when setting it up on another computer or server?

Developers include a file named **`.env.example`**. It shows the exact variable names required by the app, but uses **fake placeholder text** instead of real passwords.

In the root of your Student API project (beside `package.json`), create **`.env.example`** with this content:

```env

# Never put your real database password or host in .env.example!
DATABASE_URL="postgresql://USER:YOUR_PASSWORD_HERE@HOST:5432/postgres?sslmode=require"
PORT=4000
```

Double-check that `.env.example` contains **zero** real passwords, real Supabase project IDs, or real connection strings.

## Part 5 — Making Another Commit

In real development, you do not just upload your project once. Every time you improve your code or documentation, you make a new **commit** and **push** it to GitHub. Let's practice that cycle now.

### Commit vs. Push — What is the difference?

Beginners often confuse **Commit** and **Push**. Keep this distinction clear:

| Action | Where it happens | Needs internet? | What it does |
| --- | --- | --- | --- |
| **Commit** | On your computer (**local repository**) | **No** | Saves a checkpoint of your changes in your local Git history. GitHub.com does **not** see it yet. |
| **Push** | From your computer to **GitHub.com** (**remote repository**) | **Yes** | Uploads your saved local commits to GitHub so the online repository matches your computer. |

You must always **Commit** your changes first before you can **Push** them to GitHub.

### Practice: Add an API endpoints table to `README.md`

Let's make a small, meaningful improvement to your project documentation.

#### 1. Edit and save `README.md`

Open `README.md` in VS Code and add an **API Endpoints** section at the bottom of the file:

```markdown
## API Endpoints

| Method | Endpoint | Description | Success Status |
| --- | --- | --- | --- |
| `GET` | `/students` | Retrieve all student records | `200 OK` |
| `GET` | `/students/:id` | Retrieve one student by ID | `200 OK` |
| `POST` | `/students` | Create a new student record | `201 Created` |
| `PUT` | `/students/:id` | Replace all editable fields of a student | `200 OK` |
| `DELETE` | `/students/:id` | Delete a student record by ID | `200 OK` |
```

- You will see `README.md` listed as modified (with a yellow dot icon).

Click **Commit to main**.

Now switch to the **History** tab in GitHub Desktop. You will see **at least two commits** listed in your repository history! Notice the small upward arrow (`↑ 1`) next to your branch or on the **Push origin** button — that arrow tells you that your computer has **1 local commit** that has not been uploaded to GitHub yet.

### How everything connects

Here is how your work in Chapters 2 and 3 leads directly into **Chapter 4**:

```text
1. Student API Project (VS Code + Express + TypeScript + Supabase Pool)
       ↓
2. Git (tracks changes & saves local commits on your computer)
       ↓
3. GitHub (stores your remote repository online without .env secrets)
       ↓
4. Chapter 4: Render Deployment Platform (connects to GitHub, builds your app, and runs it online)
```

### Important facts before Chapter 4

1. **Uploading code to GitHub does NOT run your server online:** GitHub stores your **source code files**, not a running Express server. Your API still only runs when you start `pnpm dev` on your computer. In **Chapter 4**, you will connect your GitHub repository to **Render**, a cloud hosting platform that will actually build and run your Express backend on a public URL.
2. **How will Render know your `DATABASE_URL` if `.env` is not on GitHub?** Because `.env` is excluded by `.gitignore` for security, Render will not get your database password from GitHub. Instead, hosting platforms like Render provide a secure **Environment Variables** settings screen in their dashboard. In Chapter 4, you will configure `DATABASE_URL` privately inside Render's settings — never inside your GitHub code.

## Troubleshooting

| Problem / What you see | How to fix it |
| --- | --- |
| `'git' is not recognized` in terminal | Close VS Code and all terminal windows completely, reopen a new terminal after installing Git, and run `git --version` again. |
| `.env` or `node_modules` shows up in GitHub Desktop **Changes** | Do **not** commit yet! Open `.gitignore` in the root of your Student API project, make sure `.env` and `node_modules/` are written on their own lines, save `.gitignore`, and check GitHub Desktop again. |
| I already committed `.env` or my database password by mistake | **Stop immediately.** Do not publish or push to GitHub. Inform your instructor, and rotate (change) your database password in Supabase right away. |
| GitHub Desktop says *"Publish repository"* failed | Check your internet connection, confirm you verified your GitHub email address, and check **File → Options → Accounts** to make sure you are signed into GitHub.com. |
| I clicked **Commit to main**, but my change is not on GitHub.com | Remember: **Commit** only saves to your computer! Click **Push origin** in the top bar of GitHub Desktop, then refresh your browser. |
| GitHub Desktop shows thousands of files from my `Desktop` or `Documents` folder | You accidentally added your parent user folder instead of your `student-api` project folder. In GitHub Desktop, right-click the repository name → **Remove...** (keep files on disk), then add **only** your `student-api` project folder. |
| Postman CRUD check fails before Git setup | Make sure `pnpm dev` is running in your Student API folder, `.env` has your working Supabase Session pooler URL from Lesson 3.1, and your internet connection can reach Supabase. |
