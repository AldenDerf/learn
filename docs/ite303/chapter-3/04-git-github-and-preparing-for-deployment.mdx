## Part A — Introduction

### Why `localhost` is not publicly accessible

When you start your server with `pnpm dev` and send requests to `http://localhost:4000/students`, the word **`localhost`** is a special networking nickname that always means *"this exact computer I am typing on right now."*

- Your Postman app can reach `localhost:4000` because Postman and your Express server are running on the **same machine**.
- If you send the link `http://localhost:4000/students` to your instructor or a classmate, it will **fail** on their computer because *their* computer is not running your Express server.
- As soon as you press `Ctrl+C`, close VS Code, or shut down your laptop, your local server stops completely.

### The purpose of deploying a backend API

**Deployment** means putting your backend application onto a cloud server that stays connected to the internet and runs your program for you. Once deployed:

- Your API receives a **public `https://` URL** (for example, `https://student-api-xxxx.onrender.com`).
- Anyone with the link (such as your instructor grading your API in Postman, or a React frontend application you build next) can send HTTP requests to your backend over the internet.
- Your cloud server connects to your existing **Supabase PostgreSQL** database in the cloud, reading and updating the same `students` table.

### How each tool fits together

Before touching any settings, make sure you understand the exact job of each tool in your workflow:

| Tool | Role in this activity | What it does (and does NOT do) |
| --- | --- | --- |
| **Git** | Local version control software | Installed on your computer. Watches your project folder and saves checkpoints (**commits**) offline. |
| **GitHub** | Online code hosting platform | Stores a copy of your Git repository in the cloud so you have an online backup and a source for deployment. **GitHub does NOT run your Express server.** |
| **GitHub Desktop** | Visual Git application | Gives you a clear graphical window on your computer to inspect changed files, create commits, and upload (`push`) to GitHub without memorizing terminal commands. |
| **Render** | Cloud application hosting platform | Connects to your GitHub repository, downloads your code, installs dependencies, runs your start command, and hosts your live Express API at a public `https://` URL. |
| **Supabase** | Cloud PostgreSQL database host | Stores your `public.students` table in the cloud. Both your local server and your deployed Render server connect to Supabase using `DATABASE_URL`. |
| **Postman** | HTTP API testing client | Sends `GET`, `POST`, `PUT`, and `DELETE` requests to your API (first on `localhost`, then on your public Render URL) so you can inspect status codes and JSON responses. |

### The overall deployment workflow

Throughout this activity, your project will move through four connected stages:

```text
Stage 1: Local Project (VS Code + Express + TypeScript + Supabase Pool)
   │  Verify CRUD works locally, support process.env.PORT,
   │  check package.json scripts, and protect .env with .gitignore
   ▼
Stage 2: Local Git Repository (Git + GitHub Desktop)
   │  Review safe files, confirm .env is excluded,
   │  and save descriptive local commits
   ▼
Stage 3: Remote GitHub Repository (GitHub.com)
   │  Publish / Push commits online so Render can read your source code
   ▼
Stage 4: Cloud Production Server (Render + Supabase + Postman)
      Connect GitHub repo to Render, add DATABASE_URL in Render Environment,
      deploy live HTTPS Web Service, and test CRUD endpoints in Postman
```

## Part B — Preparing the Existing Student API

Never publish or deploy a project before verifying that it works locally, supports cloud port assignment, has valid startup scripts, and excludes private credentials. Complete all eight preparation steps below in your existing **Activity 3.3 Student API** project.

### Step 2 — Confirm that existing CRUD operations work locally

Start your local development server:


Open **Postman** and run a quick readiness check against `http://localhost:4000/students` using **fictional student records only**:

| Local Readiness Check | Request in Postman | Expected Result |
| --- | --- | --- |
| **1. Read all (`GET`)** | `GET http://localhost:4000/students` | **200 OK** with a JSON array of student rows from Supabase. |
| **2. Create (`POST`)** | `POST http://localhost:4000/students` with a new disposable fictional student JSON body | **201 Created** with the newly inserted row and its generated `id`. |
| **3. Read one (`GET`)** | `GET http://localhost:4000/students/{new-id}` | **200 OK** with that same student object. |

**Checkpoint:** All CRUD routes work locally against Supabase before you change any deployment settings. If any route fails locally, fix your Activity 3.3 code first—deploying broken code to Render will only produce broken cloud routes.

### Step 3 — Ensure your server supports `process.env.PORT`

On your laptop, you probably chose port `4000`. However, when **Render** runs your server in the cloud, Render automatically assigns its own port number through an environment variable named **`PORT`** (`process.env.PORT`). If your code hard-codes `app.listen(4000)` and ignores `process.env.PORT`, Render may fail to detect your running service.

Open `src/server.ts` and inspect how your port is defined:

```typescript
// Read Render's assigned PORT in production, or fall back to 4000 on your laptop
const PORT = Number(process.env.PORT) || 4000;

app.listen(PORT, () => {
  console.log(`Student API listening on port ${PORT}`);
});
```

**Why this works:**
- On your computer, if `PORT` is not set (or is set to `4000` in `.env`), `PORT` becomes `4000`.
- On Render, Render injects its own `process.env.PORT` value automatically, and your Express server listens on the exact port Render expects.

### Step 4 — Inspect `package.json` and verify build and production startup scripts

When Render deploys your repository, it needs to know how to **install packages**, how to **build** your project (if needed), and how to **start** your server in production.

Open `package.json` in your Student API project and inspect three sections:

1. **Dependencies vs. DevDependencies:**
   - Ensure runtime packages (`express`, `pg`, `dotenv`) are under `"dependencies"`.
   - Look at how your TypeScript code runs. There are two common ways students set up TypeScript in Express:

#### Option A — Compiling TypeScript to JavaScript (Recommended for production)

In this standard production pattern, TypeScript (`tsc`) compiles your `src/*.ts` files into plain JavaScript inside a `dist/` folder during the **build** step, and Node.js runs the compiled JavaScript during the **start** step.

If your `tsconfig.json` has `"rootDir": "./src"` and `"outDir": "./dist"` (or if you add them now), your `package.json` scripts can look like this:

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "build": "tsc",
    "start": "node dist/server.js"
  }
}
```

#### Option B — Running TypeScript directly with `tsx`

If your project does not emit a `dist/` folder and instead runs `src/server.ts` directly with `tsx`, your `package.json` scripts might look like this:

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "build": "tsc --noEmit",
    "start": "tsx src/server.ts"
  }
}
```

*(Note: If `"start"` uses `tsx`, make sure `tsx` is available when Render runs—either move `tsx` into `"dependencies"` or ensure Render installs devDependencies during the build step.)*

#### Test your build and start scripts locally!

Before moving on, stop `pnpm dev` (`Ctrl+C`) and test your exact production commands in your VS Code terminal:

```powershell
# 1. Test your build script
pnpm build

# 2. Test your production start script
pnpm start
```

**Checkpoint:** Both `pnpm build` and `pnpm start` succeed on your computer without errors, and `GET http://localhost:4000/students` still returns `200 OK` while `pnpm start` is running. Stop `pnpm start` with `Ctrl+C` when finished.

### Step 5 — Protect `.env` using `.gitignore`

Your `.env` file holds your real Supabase `DATABASE_URL` and database password. A **`.gitignore`** file is a plain text file in your project root that tells Git which files and folders it must **ignore** and **never track or upload**.

Check the root of your Student API project (beside `package.json`). Create or update **`.gitignore`** (starts with a dot `.`, with no `.txt` extension) so it contains at least these rules:

```gitignore
# Dependency directory (recreated automatically during install)
node_modules/

# Private environment variables and database credentials (NEVER commit!)
.env
.env.*
!.env.example

# Compiled build output and log files
dist/
*.log

# Operating system metadata files
.DS_Store
Thumbs.db
```

**Why each rule matters:**
- `node_modules/` contains thousands of downloaded library files. Uploading it wastes bandwidth and slows down Git; Render will install dependencies automatically from `package.json` and `pnpm-lock.yaml`.
- `.env` and `.env.*` block your real database credentials from ever entering Git.
- `!.env.example` makes an exception so Git *does* allow the safe placeholder file `.env.example`.
- `dist/` excludes compiled JavaScript output so your repository stays clean and Render builds fresh code on every deploy.

### Step 6 — Understand and create `.env.example`

Because `.env` is ignored by Git, anyone inspecting your repository (or setting it up on another machine) needs to know *which* environment variable names your program expects without seeing your real secret values.

Create or inspect **`.env.example`** in your project root beside `package.json`:

```env
# Copy this file to .env for local development.
# On Render, add DATABASE_URL in the Render Environment dashboard.
# NEVER put real database passwords or private hostnames in this file!
DATABASE_URL="postgresql://USER:YOUR_PASSWORD_HERE@HOST:5432/postgres?sslmode=require"
PORT=4000
```

Confirm that `.env.example` contains **only fake placeholder text** and zero real passwords or Supabase project IDs.

### Step 8 — Verify that credentials are not tracked by Git (Security Risks & Response)

Before opening GitHub Desktop, understand why credential security is one of the most important skills in backend engineering:

- **What is the security risk?** Automated bots constantly scan GitHub repositories within seconds of a push looking for leaked `.env` files, `postgresql://` connection strings, and API keys. If your real `DATABASE_URL` is uploaded to GitHub, unauthorized users can read, modify, or wipe your database, or abuse your cloud account.
- **Why `.gitignore` only protects untracked files:** Adding `.env` to `.gitignore` stops Git from adding `.env` in the future. However, if `.env` was *already committed* before you added `.gitignore`, Git continues tracking it and keeps the password inside your commit history!

<Callout type="warning">

**What to do if you accidentally committed `.env` or a real password:**

1. **STOP immediately.** Do **not** publish or push your repository to GitHub.
2. **Rotate (change) your database password immediately** in your Supabase dashboard (**Project Settings → Database → Database password**) so the leaked password becomes useless right away.
3. **Update your local `.env`** with the new password and confirm `.env` is listed in `.gitignore`.
4. **Inform your instructor** before pushing so they can help you verify that `.env` is untracked and no secret remains in your commit history. Never rely on deleting `.env` in a later commit—anyone viewing an older commit on GitHub can still read the old password!

</Callout>

If Git is already initialized in your project folder, you can run this quick terminal check to verify what Git sees:

```powershell
# Check Git status (if your folder is already a Git repository)
git status --ignored
```

**Checkpoint:** `.env` and `node_modules/` appear under **Ignored files** (or do not appear as tracked/staged files), `.env.example` uses placeholders only, and `src/db.ts` reads `process.env.DATABASE_URL` instead of hard-coding any connection string.

## Part C — Git and GitHub Desktop

Now that your project is tested and your secrets are protected, you will use **Git** and **GitHub Desktop** to track your project and publish it to **GitHub**.

### Understanding Git vs. GitHub and core vocabulary

Review these essential version control terms before creating your repository:

| Concept | Clear explanation |
| --- | --- |
| **Git vs. GitHub** | **Git** is the version-tracking tool installed on your computer (works offline). **GitHub** is the cloud website (`github.com`) that hosts your Git repositories online (requires internet). |
| **Repository (repo)** | A project folder tracked by Git, including its files and complete history of saved checkpoints. |
| **Commit** | A saved snapshot (checkpoint) of your tracked files on your computer at a specific moment, labeled with a clear summary message. |
| **Push** | Uploading your saved local commits from your computer to your remote repository on GitHub. |
| **Pull** | Downloading new commits from GitHub to update the local repository on your computer. |
| **Branch** | An independent timeline of commits inside a repository. Your primary working timeline is called the **`main` branch**. |

<Callout type="info">

**Prerequisite check:** Make sure **Git** (`git --version` in PowerShell), a verified **GitHub.com account**, and **GitHub Desktop** (signed into your GitHub account under **File → Options → Accounts** with your Git Name and Email configured) are ready on your computer.

</Callout>

## Part D — Deploying to Render

Now you will connect your GitHub repository to **Render** so Render can build and run your Express server on a public `https://` URL. Because cloud dashboards update their visual layouts over time, practice reading the labels on screen rather than relying on memorized button coordinates.

### Step 1 — Create a Render account and start a new Web Service

1. Open [https://render.com](https://render.com) in your browser and sign in (signing in with your **GitHub account** is the easiest way to connect your repositories).
2. Open the **Render Dashboard**.
3. Click the **New +** (or **Add new**) button and select **Web Service**.
   - *Why a Web Service?* A **Static Site** only serves plain HTML/CSS/JS files to browsers. Because your Express API is a persistent Node.js server that listens for HTTP requests and queries PostgreSQL, it must be deployed as a **Web Service**.

### Step 2 — Connect your GitHub repository and select the branch

1. Choose the option to **Build and deploy from a Git repository**.
2. Connect your GitHub account if prompted and grant Render access to your **Student API repository**.
3. Select your **Student API repository** from the list.
4. Set the configuration basics:
   - **Name:** Give your service a clear name (for example, `ite303-student-api-yourname`). Render uses this name in your public `.onrender.com` URL.
   - **Language / Runtime:** Select **`Node`** (Node.js environment).
   - **Branch:** Select **`main`** (or whichever branch holds your verified commits).
   - **Region:** Choose a nearby region (such as **Singapore** or the closest region to your Supabase project).
   - **Root Directory:** Leave blank *unless* your `package.json` is nested inside a subfolder in your repository.
   - **Instance Type:** Select the **Free** plan for classroom practice.

### Step 3 — Configure Build Command and Start Command

Scroll to the **Build Command** and **Start Command** fields in Render.

<Callout type="important">

**Commands depend on your actual project configuration!** Inspect your own `package.json` from Part B Step 4 so the commands you give Render match the exact package manager and scripts in your repository.

</Callout>

Compare the common configurations below and enter the commands that match **your** Student API project:

| Project Setup | Typical Build Command on Render | Typical Start Command on Render |
| --- | --- | --- |
| **TypeScript compiled to `dist/` with `pnpm`** (Option A in Part B) | `pnpm install && pnpm run build` | `pnpm run start` *(which runs `node dist/server.js`)* |
| **TypeScript run via `tsx` with `pnpm`** (Option B in Part B) | `pnpm install` *(or `pnpm install --prod=false` if `tsx` is in devDependencies)* | `pnpm run start` *(which runs `tsx src/server.ts`)* |
| **Project using `npm` instead of `pnpm`** | `npm install && npm run build` | `npm run start` |

**Ask yourself before continuing:**
- Does my `package.json` actually have a `"build"` script if I put `pnpm run build` in the Build Command?
- Does my `package.json` actually have a `"start"` script? (Never use `pnpm dev` or `tsx watch` as your production Start Command on Render—file watchers waste memory and can cause production containers to fail.)

### Step 4 — Add the `DATABASE_URL` environment variable securely

Because `.env` was excluded by `.gitignore`, Render does not know how to connect to your Supabase database yet. You must provide `DATABASE_URL` inside Render's secure **Environment Variables** settings.

1. Scroll down to the **Environment Variables** section in Render and click **Add Environment Variable**.
2. Set the variable key and value:
   - **Key:** `DATABASE_URL` (must match `process.env.DATABASE_URL` in your `src/db.ts` file with exact uppercase spelling).
   - **Value:** Paste your working **Supabase Session pooler connection string** from your local `.env` file (without surrounding quotation marks `"..."`).
3. Verify two critical details in your `DATABASE_URL` value:
   - It uses your **Supabase Session pooler** host (for example, `...pooler.supabase.com:5432/postgres?sslmode=require`), which supports IPv4 connections from Render's free tier.
   - It contains your real database password (properly URL-encoded if your password has special characters), **not** the `[YOUR-PASSWORD]` placeholder.
4. *(Do **not** manually set `PORT` unless required—Render sets `PORT` automatically.)*

### Step 5 — Start deployment and read the build and runtime logs

1. Click **Create Web Service** (or **Deploy Web Service**) at the bottom of the page.
2. Render will open the **Logs** screen for your deployment. Practice reading the logs from top to bottom—they tell the story of your deployment in two phases:
   - **Build Phase:** Render clones your GitHub commit on `main`, installs Node.js packages (`pnpm install`), and runs your Build Command (`pnpm run build`). Look for `Build successful 🎉`.
   - **Deploy / Runtime Phase:** Render starts your container using your Start Command (`pnpm run start`). Look for your Express startup log (such as `Student API listening on port ...`) and your database connection message, followed by Render reporting **`Your service is live 🎉`**.

### Step 6 — Find your public HTTPS URL

Once your service badge turns green (**Live**), look near the top-left of your Render Web Service dashboard (right underneath your service name). You will see a public HTTPS link formatted like:

```text
https://ite303-student-api-yourname.onrender.com
```

Copy this URL. Notice two things:
1. It uses **`https://`** (encrypted HTTP), not `http://`.
2. You do **not** write `:4000` or `:10000` at the end of a Render URL—Render routes standard HTTPS traffic to your internal `process.env.PORT` automatically.

<Callout type="info">

**Note on Render's Free tier spin-down:** Free Web Services on Render automatically go to sleep after about 15 minutes of inactivity. The **first request** you send after a quiet period may take **30–60 seconds** while Render wakes up the server. Subsequent requests will respond quickly.

</Callout>

**Checkpoint:** Your Render Web Service status is **Live**, your logs show no crash loops, and you have copied your public `https://<your-service>.onrender.com` URL.

## Part E — Live API Testing with Postman

Deploying a server is not complete until you verify that every endpoint works against the live cloud URL and persists changes in your Supabase database.

### Important testing rules

1. **Test against your deployed Render URL, NOT `localhost`:** Every request in this section must start with `https://<your-service>.onrender.com/students`.
2. **Use disposable fictional test records only:** Create new fictional test records (for example, `"student_number": "2026-901"`, `"first_name": "Test"`, `"last_name": "Deploy"`) for your update and delete tests.
3. **Do NOT delete existing baseline or production records:** Only `DELETE` the disposable fictional test record that you created with `POST` during this test run.

### Required live Postman test sequence

Create or update a Postman Collection for your deployed API and execute all seven test cases below in order:

| Test # | Method & Live Endpoint | Request Body / Details | Required Status | Expected Response & Verification |
| --- | --- | --- | --- | --- |
| **1** | `GET /students` | None | **`200 OK`** | Returns a JSON array of existing student records from your Supabase `students` table. |

### How to diagnose where an error comes from

When a live test fails, beginners often guess randomly. Instead, use the clues in Postman and Render logs to identify which of the **four layers** produced the error:

| Layer | Symptoms you see | How to confirm & fix |
| --- | --- | --- |
| **1. Postman (Client mistake)** | • `Could not send request` / DNS error (typo in URL)<br/>• `404 Cannot POST /student` (missing `s` in `/students`)<br/>• `400` on `POST`/`PUT` even though JSON looks right (`Body` tab is set to `Text` instead of `raw → JSON`, so `Content-Type: application/json` was not sent) | Check the HTTP method dropdown, the exact spelling of `https://<your-service>.onrender.com/students`, and confirm **Body → raw → JSON** is selected. Notice whether the request ever appears in your Render logs—if Render logs show nothing, the request never reached your Express server! |
| **2. Render (Hosting / Platform layer)** | • `502 Bad Gateway` or `503 Service Unavailable`<br/>• Browser/Postman hangs for 60+ seconds and fails<br/>• Render dashboard badge says **Deploy failed** or **Exited** | Open the **Render Logs** tab. Your container either failed to build, crashed on startup (for example, wrong Start Command or missing `DATABASE_URL`), or is still waking up from Free-tier sleep. |
| **3. Express (Application / Route / Validation layer)** | • Response arrives quickly as JSON with `400 Bad Request` or `404 Not Found`<br/>• Default Express HTML `Cannot GET /...` | Your Render container is running and Express answered! Check your route path in `studentRoutes.ts`, middleware order (`app.use(express.json())`), and validation rules in `studentController.ts`. |
| **4. PostgreSQL / Supabase (Database layer)** | • Response is `500 Internal Server Error` (e.g., `{ "message": "Could not fetch students" }`) or `409 Conflict` (`student_number already exists`)<br/>• Render logs show `password authentication failed`, `ENETUNREACH` (IPv6 direct URL used instead of Session pooler), or `relation "students" does not exist` | Express reached the `pool.query(...)` step, and PostgreSQL or `pg` returned an error. Check the **Render Logs** for the server-side error details, verify `DATABASE_URL` in Render's Environment tab uses the **Session pooler** URL with `sslmode=require`, and check your Supabase table. |

**Checkpoint:** All seven required Postman tests return their expected status codes against your live `https://<your-service>.onrender.com` URL.

## Part F — AI-Assisted Troubleshooting

In professional software development, engineers read documentation, inspect logs, and sometimes ask AI assistants (such as ChatGPT, Claude, or Gemini) to help explain unfamiliar errors. However, pasting errors blindly without understanding the fix—or leaking database passwords into an AI chat—is dangerous and ineffective.

### The 7-Step Responsible AI Troubleshooting Workflow

Whenever you hit a deployment or testing error that you cannot solve immediately, follow these seven steps in order:

1. **Read the original error message carefully:** Look at the exact wording, file name, line number, or HTTP status code in your terminal, Render logs, or Postman response.
2. **Identify the failing component:** Use the table in Part E to decide whether the failure is happening in **Git/GitHub**, the **Render Build phase**, the **Render Start/Runtime phase**, **Express routing/validation**, **Supabase PostgreSQL**, or **Postman**.
3. **Ask an AI assistant a clear, sanitized technical question:** Describe what you are trying to do, your tech stack (Node.js, Express, TypeScript, `pg`, Render), the exact **sanitized** error message, and the relevant code or script snippet.
4. **Evaluate the suggested explanation:** Does the AI's explanation match how your project is actually structured? (For example, if the AI suggests Prisma or Mongoose commands, reject that part because our project uses the `pg` Pool directly.)
5. **Make changes carefully:** Apply only the small change you understand, test it locally if it is a code/script change, and create a clear Git commit + push.
6. **Retest the application:** Verify in Render logs and Postman whether the fix actually resolved the problem and did not break existing routes.
7. **Explain what actually solved the problem:** Write down the root cause and the fix in your own words for your activity reflection.

<Callout type="warning">

**Strict AI Security Rule: NEVER paste passwords or private connection strings into AI tools!**

Before copying any terminal output, `.env` line, or Render log into an AI prompt, **always replace sensitive values with placeholders**:
- **UNSAFE (Never do this):** `My DATABASE_URL is postgresql://postgres.abcdefgh:MySecretPass123@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres`
- **SAFE (Sanitized):** `My DATABASE_URL format is postgresql://USER:REDACTED_PASSWORD@HOST:5432/postgres?sslmode=require`

</Callout>

### Realistic troubleshooting examples

Study these five common deployment problems, what causes them, and how to ask an AI assistant a meaningful, safe question about each one:

#### Scenario 1 — Build failure on Render (`tsc: not found` or TypeScript error)

- **What you see in Render Build Logs:**
  ```text
  sh: 1: tsc: not found
  ==> Build failed 😞
  ```
- **Failing component:** Render Build phase (`package.json` dependencies / build script).
- **Good sanitized AI prompt:**
  > *"I am deploying a Node.js + Express + TypeScript API to Render using `pnpm`. My Render Build Command is `pnpm install && pnpm run build`, and `"build": "tsc"` is in my `package.json`. Render fails with `sh: 1: tsc: not found`. `typescript` is listed in `devDependencies`. Why can't Render find `tsc`, and how should I configure my dependencies or Render settings?"*
- **What to verify:** Check whether `typescript` (and `@types/*`) were installed during the build, or whether `NODE_ENV=production` skipped `devDependencies`.

#### Scenario 2 — Incorrect Start Command (`Cannot find module '.../dist/server.js'`)

- **What you see in Render Deploy Logs:**
  ```text
  Error: Cannot find module '/opt/render/project/src/dist/server.js'
  ==> Exited with status 1
  ```
- **Failing component:** Render Start phase (`package.json` `"start"` script vs. `tsconfig.json` `"outDir"`).
- **Good sanitized AI prompt:**
  > *"My Express + TypeScript app builds on Render without errors, but when Render runs `node dist/server.js`, it exits with `Error: Cannot find module '/opt/render/project/src/dist/server.js'`. Here is my `tsconfig.json`: `[paste tsconfig.json]`. Why wasn't `dist/server.js` created where Node expects it?"*
- **What to verify:** Check if `tsconfig.json` had `"noEmit": true` (which prevents `tsc` from creating files) or if `"outDir": "./dist"` was missing.

#### Scenario 3 — Missing or misspelled environment variable on Render

- **What you see in Render Deploy Logs:**
  ```text
  Error: Missing DATABASE_URL environment variable
  ==> Exited with status 1
  ```
- **Failing component:** Render Environment Variables configuration.
- **How to verify and fix:** Look at `src/db.ts` where `process.env.DATABASE_URL` is checked. Open Render's **Environment** tab and verify that `DATABASE_URL` is added, spelled in exact uppercase, and saved—then trigger a redeploy if needed.

#### Scenario 4 — Database connection error (`ENETUNREACH` or authentication error)

- **What you see in Render Runtime Logs when calling `GET /students`:**
  ```text
  Error: connect ENETUNREACH 2406:da18:...:5432
  ```
  *(or Postman receives `500 Internal Server Error`)*
- **Failing component:** Supabase PostgreSQL connection string (`DATABASE_URL` on Render).
- **Good sanitized AI prompt:**
  > *"My Express API on Render uses the `pg` Pool to connect to Supabase PostgreSQL. Requests return 500 and the Render logs show `connect ENETUNREACH` followed by an IPv6 address on port 5432. Why does this happen on Render, and which Supabase connection string type should I use instead? (Credentials redacted.)"*
- **What to verify:** Render's outbound network uses IPv4, while Supabase's direct connection host is IPv6-only by default. Switching `DATABASE_URL` in Render to the **Supabase Session pooler** connection string (`...pooler.supabase.com:5432/postgres?sslmode=require`) resolves the issue.

#### Scenario 5 — HTTP 400 or 404 error during live Postman testing

- **What you see in Postman:**
  Sending `POST https://<your-service>.onrender.com/students` returns `400 Bad Request` with `{ "message": "A JSON object is required" }` or `{ "message": "All text fields are required" }`.
- **Failing component:** Postman request formatting vs. Express controller validation.
- **How to verify and fix:** Inspect Postman's **Body** tab (confirm **raw** and **JSON** are selected so `Content-Type: application/json` is sent) and compare every field name in your JSON against the five properties expected by `createStudent` (`student_number`, `first_name`, `last_name`, `course`, `year_level`).
