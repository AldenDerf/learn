## 2. Understand the PUT update before coding (15 minutes)

**CRUD** names four common actions on stored data: **Create** a row (POST), **Read** a row (GET), **Update** a row (PUT), and **Delete** a row (DELETE). PUT asks the server to replace the editable fields of the student identified by the URL. Send **all five fields**, even if only one value changes. The database-generated `id` is not in the JSON body and does not change. PATCH is outside this lab.

For `PUT /students/7`, Express matches `/:id`; `req.params.id` is the text `"7"` from the **URL**. We must check and convert it to a positive integer. The JSON under Postman's **Body → raw → JSON** becomes `req.body` after `express.json()` runs. We must check its shape and fields before writing. A missing field is an error for this full replacement request.

PostgreSQL's `UPDATE` changes rows. **`WHERE id = $6` limits the change to one ID. Without `WHERE`, an UPDATE could change every student.** `$1`–`$6` are placeholders: `pg` sends the six checked values separately from the SQL text, in array order. Do not join user input into SQL strings. `RETURNING` asks PostgreSQL to give back the row it changed. If it returns no rows, no student matched that ID.

```sql
UPDATE students
SET student_number = $1, first_name = $2, last_name = $3,
    course = $4, year_level = $5
WHERE id = $6
RETURNING id, student_number, first_name, last_name, course, year_level;
```

This query uses the existing `students` table. It does not create a new row. A successful update returns **200 OK** with the updated row. Invalid input returns **400 Bad Request**; a valid but unused ID returns **404 Not Found**. The table's `UNIQUE` rule for `student_number` can reject a number owned by another row; that conflict returns **409 Conflict**. Unexpected database failures return **500** with a safe, general message.

**Think before you edit:** Which part of the request selects the row? Which part supplies its new details? What could happen if `WHERE` were missing?

## 4. Replace only the PUT controller (30 minutes)

Open `src/controllers/studentController.ts`. Keep its Express `Request` and `Response` imports, the `pool` import from `../db`, and **all three working GET/POST functions**. Replace only the old `updateStudent` acknowledgement function with this complete handler. If the old function has another name, use that name in both the router and controller.

```typescript
export async function updateStudent(req: Request, res: Response): Promise<void> {
  // The route parameter is text; accept only a positive, safe whole-number ID.
  const idText = req.params.id;
  const id = Number(idText);
  if (!/^\d+$/.test(idText) || !Number.isSafeInteger(id) || id < 1) {
    res.status(400).json({ message: 'Student ID must be a positive integer' });
    return;
  }

  // The JSON middleware puts Postman's request body in req.body.
  const body: unknown = req.body;
  // Full PUT requires a JSON object, not an array or a missing body.
  if (typeof body !== 'object' || body === null || Array.isArray(body)) {
    res.status(400).json({ message: 'A JSON object is required' });
    return;
  }

  // Read all five editable fields from the checked object.
  const { student_number, first_name, last_name, course, year_level } = body as Record<string, unknown>;
  // Stop before SQL if any required text field is blank or missing.
  if (typeof student_number !== 'string' || student_number.trim() === '' ||
      typeof first_name !== 'string' || first_name.trim() === '' ||
      typeof last_name !== 'string' || last_name.trim() === '' ||
      typeof course !== 'string' || course.trim() === '') {
    res.status(400).json({ message: 'All text fields are required' });
    return;
  }

  // Match Lesson 3.2: year_level must be a positive whole number.
  if (typeof year_level !== 'number' || !Number.isInteger(year_level) ||
      year_level < 1) {
    res.status(400).json({ message: 'year_level must be a positive whole number' });
    return;
  }

  // $1–$5 are replacement values; $6 is the checked ID in WHERE.
  // WHERE protects other rows; RETURNING gives back the changed row.
  const sql = `UPDATE students
    SET student_number = $1, first_name = $2, last_name = $3,
        course = $4, year_level = $5
    WHERE id = $6
    RETURNING id, student_number, first_name, last_name, course, year_level;`;
  const values = [
    student_number.trim(), first_name.trim(), last_name.trim(),
    course.trim(), year_level, id
  ];

  try {
    // pg sends the values separately from the SQL command.
    const result = await pool.query(sql, values);
    // No returned row means that this valid ID was not found.
    if (result.rows.length === 0) {
      res.status(404).json({ message: 'Student not found' });
      return;
    }
    // 200 OK includes the row that PostgreSQL actually updated.
    res.status(200).json(result.rows[0]);
  } catch (error: unknown) {
    // PostgreSQL code 23505 means another row owns this student number.
    if (typeof error === 'object' && error !== null &&
        'code' in error && error.code === '23505') {
      res.status(409).json({ message: 'student_number already exists' });
      return;
    }
    // Do not send a raw database error or private connection details.
    res.status(500).json({ message: 'Could not update student' });
  }
}
```

The `return` statements stop the handler after a response. The `WHERE` value is **sixth** because five replacement fields come first. PostgreSQL error code `23505` means a uniqueness violation. The response does not expose the raw database error, connection string, or password. This guided handler matches the positive-whole-number rule in the 3.2 example. If your 3.2 challenge added a **1–4** limit, add `year_level > 4` to the PUT condition and test that boundary too. Keep the POST code you already have.

## 6. Add DELETE for one student (45 minutes)

**Objective:** Remove one **disposable fictional practice row** and confirm which row PostgreSQL removed. First use POST to create that practice row, write down its returned ID, and leave the updated row from Section 5 untouched. DELETE needs an ID in the URL but no JSON request body.

Before writing Express code, read the SQL. `DELETE FROM` removes rows, `WHERE id = $1` selects one checked ID, and `RETURNING` gives back the removed row. Here `$1` is a **placeholder**; `pg` sends the ID separately in a values array. Never leave out `WHERE`.

```sql
DELETE FROM students
WHERE id = $1
RETURNING id, student_number;
```

### Step B — Replace only the DELETE controller

Open `src/controllers/studentController.ts`. Keep the existing Express type imports, `pool` import, and all GET, POST, and PUT functions. Replace the old `deleteStudent` acknowledgement function with this handler. If your old handler uses a different name, use that same name in both files.

```typescript
export async function deleteStudent(req: Request, res: Response): Promise<void> {
  // Read the ID after /students/ in the request URL.
  const idText = req.params.id;
  const id = Number(idText);

  // Stop if the ID is not a positive, safe whole number.
  if (!/^\d+$/.test(idText) || !Number.isSafeInteger(id) || id < 1) {
    res.status(400).json({ message: 'Student ID must be a positive integer' });
    return;
  }

  // $1 is the checked ID; WHERE protects all other rows.
  // RETURNING lets us confirm which row PostgreSQL removed.
  const sql = `DELETE FROM students
    WHERE id = $1
    RETURNING id, student_number;`;

  try {
    // Send the ID separately from the SQL text.
    const result = await pool.query(sql, [id]);

    // No returned row means this valid ID did not exist.
    if (result.rows.length === 0) {
      res.status(404).json({ message: 'Student not found' });
      return;
    }

    // 200 OK confirms the ID and fictional number that were deleted.
    res.status(200).json({
      message: 'Student deleted',
      id: result.rows[0].id,
      student_number: result.rows[0].student_number
    });
  } catch {
    // Hide unexpected database details from the response.
    res.status(500).json({ message: 'Could not delete student' });
  }
}
```

The handler does **not** read `req.body`, because the URL already tells it which row to remove. A valid ID with no matching row returns **404**. A successful request returns **200** and a simple confirmation. A database failure returns a safe **500** message; it does not claim a deletion succeeded.

**Expected result:** `DELETE http://localhost:4000/students/{your-disposable-id}` returns a body like `{ "message": "Student deleted", "id": 8, "student_number": "2026-208" }`. Your ID and fictional number will differ.

**Checkpoint:** GET that same ID now returns **404** and `{ "message": "Student not found" }`. GET all still works. In Supabase SQL Editor, a read-only SELECT for the removed ID returns no rows. The PUT-updated row should still be present.

**If stuck:** A 404 on DELETE may mean you used the wrong ID or already deleted it. An old acknowledgement means the old route or controller still runs. A 500 calls for checking the same Supabase connection used by GET; keep credentials out of screenshots and messages.
