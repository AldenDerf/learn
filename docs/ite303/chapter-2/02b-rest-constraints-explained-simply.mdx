## Start with Your Student Information API

In [2.2.1 Understanding REST API Design](/web-systems/chapter-2/understanding-rest-api-design), you learned to use clear routes such as `GET /students` instead of `GET /getStudents`. In [Lab 2.1](/web-systems/chapter-2/lab-2-1), your server answered requests like this:

```text
Browser / app
    | GET /students
    v
  Server
    | JSON response
    v
Browser / app
```

You can create a route. But as an application grows, **how should the client and server communicate so the system stays understandable?** Clear route names help, but they answer only part of that question.

**REST is a way to design how parts of a web system communicate.** Software engineers call it an *architectural style*. That means a set of design boundaries, or **constraints**, for the system as a whole. REST is not a programming language, Express, or JSON. We will discover its six constraints through the same Student Information API.

## 1. Different Jobs

Imagine changing the color of a student card on the page. Should that require a change to the API server? Usually no. The page decides how to display information; the server answers requests for information.

```text
CLIENT                    SERVER
Displays student cards    Receives GET /students
Handles clicks            Prepares a response
```

The two sides agree on how to communicate. The page can change its display without necessarily changing the API. The server can change its internal work without necessarily changing the response the client expects.

This separation is the **Client–Server** constraint. Remember: **different jobs, agreed communication.**

**Think:** If the page changes from a list to cards, must `GET /students` change?

<details>
<summary>Check your thinking</summary>

Usually no. The client can present the same information differently while keeping the API agreement.

</details>

## 2. What If Another Server Gets the Next Request?

Picture two requests:

```text
Request 1: Client -> Server A
           "My selected course is BSIT. Remember it."

Later...

Request 2: Client -> Server B
           "Show students from my selected course."

Server B:  "Which course? I did not hear Request 1."
```

The second request makes sense only if the server remembers an earlier conversation. What if it reaches a different server, or that memory is gone? The request becomes unclear.

Now put the needed course in the request itself:

```text
Client -> Server A: GET /students?course=BSIT
Client -> Server B: GET /students?course=BSIT
```

Either server can see which course was requested. In Lab 2.1, that route reads the `course` query value and echoes it. The lab does not store students; this example is about the request, not a database.

This idea is called **Stateless**: each request carries the information needed to understand and process it, instead of depending on hidden conversation state from a previous request.

**Stateless does not mean the server cannot save anything.** A database may store a fact such as “Student Juan belongs to BSIT.” That is student information. The problem above is different: the server must remember *which course this client chose earlier* just to understand the next request. Authentication is not automatically incompatible with statelessness either; needed request context can be supplied with a request.

Remember: **do not make the next request depend on a hidden previous conversation.** An in-memory student array alone would not prove that requests are stateless.

**Think:** A client first says “Remember BSIT,” then later says “Show my course's students.” What could go wrong? How would you change the second request?

<details>
<summary>Check your thinking</summary>

Another server might not know the earlier selection. Send `GET /students?course=BSIT` so the needed filter travels with the request. This illustrates Stateless.

</details>

## 3. Do We Need the Same Response Again?

Suppose the public course list has not changed:

```text
Student A -> GET /courses -> same course list
5 seconds later:
Student A -> GET /courses -> same course list
Student B -> GET /courses -> same course list
```

Must every request fetch and prepare the same information again? Sometimes a client or another cache can keep an earlier response and reuse it **when the response's rules allow it**.

```text
First time:  request -> server -> response saved if allowed
Later:       valid saved response -> reuse it
             otherwise -> ask server again
```

Keeping a response for possible reuse is **caching**. The **Cacheable** constraint says responses should tell clients and caches whether reuse is allowed and under what rules. This can reduce repeated work and network traffic, and may make a response faster.

For example, a hypothetical public course-list response could say:

```http
Cache-Control: public, max-age=60
```

An allowed copy may be treated as fresh for 60 seconds. A response that should not be stored could say:

```http
Cache-Control: no-store
```

These headers are **examples**, not features of Lab 2.1. A public, rarely changing list may be reusable. Private student information or fast-changing information needs a different policy. Cacheable does **not** mean “cache everything.” You do not need to memorize the headers now.

Remember: **can I safely reuse an earlier response?**

**Think:** A public course list is requested 20 times in one minute and has not changed. What could reduce repeated work? Would you automatically apply the same rule to private student information?

<details>
<summary>Check your thinking</summary>

An allowed cached response could be reused. Private information needs its own careful reuse rules; we cannot assume the same policy fits. This illustrates Cacheable.

</details>

## 4. Can Another Developer Predict the API?

Imagine finding these routes in a new project:

```text
GET  /getStudents
POST /makeNewStudent
GET  /studentSearchByNumber/3
GET  /giveMeCourses
```

Could you easily guess the next route? Compare the pattern you planned in 2.2.1:

```text
GET  /students
GET  /students/3
POST /students
GET  /courses
```

Here the path identifies the resource, the HTTP method tells us the requested action, and the response carries information about that resource. A **representation** is the information sent about a resource, such as JSON about student 3. Consistent messages help clients and servers understand each other.

This points toward the **Uniform Interface** constraint. Beginner memory phrase: **use consistent rules so communication is predictable.** Clear resource routes are useful, but the formal constraint covers more than route naming. See the short note below when you are ready.

**Think:** Why can `GET /students/3` be easier to guess after you have seen `GET /students`?

<details>
<summary>Check your thinking</summary>

Both follow one resource pattern: `/students` for the collection and `/students/3` for one student. The method still says what the client asks to do.

</details>

### Going Further: REST Is Deeper Than Route Naming

The formal Uniform Interface also involves identifying resources, working with them through representations, self-descriptive messages, and **hypermedia-driven transitions**. The last idea is often called HATEOAS: a response can guide a client toward meaningful next actions. You do not need to implement or memorize HATEOAS in this lesson. An arbitrary `links` field alone does not prove that an API follows the formal constraint.

## 5. What If There Is a Gateway?

The client thinks, “I send a request to the system.” Inside, another component might pass it along:

```text
Client
  |
Gateway / proxy
  |
API server
```

The client does not need to know every internal component. Each component communicates through the layer it can see. This is the **Layered System** constraint. Remember: **you only need to understand the layer you communicate with.**

Putting Express files in `routes/`, `controllers/`, or `services/` folders organizes code *inside one application*. Those folders do not, by themselves, prove REST's Layered System constraint. We will discuss code organization in 2.2.3.

## 6. Can the Server Send Code to Run?

A server may send executable code to extend what a client can do. JavaScript sent to a browser is a familiar example. This is **Code on Demand**, an **optional** REST constraint. Remember: **the server may optionally send code to run.**

Ordinary JSON student data is not executable code. Lab 2.1 does not need Code on Demand.

## REST in One Story

A student opens the Student Information app:

1. The client displays the page; the server answers API requests. **Client–Server.**
2. The client sends `GET /students?course=BSIT`. The course is in this request. **Stateless.**
3. A response about public information says whether a saved copy may be reused. **Cacheable.**
4. `GET /students` and `GET /students/3` follow understandable resource rules. **Uniform Interface** is broader, but these routes help.
5. A gateway could pass the request along without the client knowing its internal details. **Layered System.**
6. The server *could* send code for the client to run, but this API does not need to. **Code on Demand is optional.**

| Constraint | Question to remember |
| --- | --- |
| Client–Server | Who has which job? |
| Stateless | Can this request be understood by itself? |
| Cacheable | Can an earlier response be reused under its rules? |
| Uniform Interface | Are we communicating with consistent rules? |
| Layered System | Must the client know every internal layer? |
| Code on Demand (optional) | Is executable code sent for the client to run? |

Express can help us build this API, and JSON can carry its responses. Neither one proves that the whole system follows REST. A clean route is a good start, not the complete architectural style.

3. A response says a saved copy can be reused for 60 seconds. Which idea is this? Should every response get the same rule?
4. Does returning JSON from Express prove that the whole API is RESTful? Why?
5. Which constraint is optional? Is JSON student data an example of it?
